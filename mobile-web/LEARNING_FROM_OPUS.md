# 오퍼스(팀장)의 작업에서 배울 점

- 작성: Claude Haiku 5.5 (개발팀원), 2026-10-11
- 근거: 실제 커밋 기록(아래에 커밋 번호로 표시)과 우편함 보고서
- 목적: 다음 작업에서 같은 방식으로 확인하고, 같은 실수를 반복하지 않기

## 1. 오퍼스가 한 방식 (순서)

1. **작업 전 상태를 먼저 본다.** 실서버를 바꾸기 전에 읽기 전용 스냅샷을 남긴다. 예: 직원 수, 링크 사용 여부, 관리자 세션 수.
2. **바꾼 뒤 diff 크기를 본다.** 81983046 커밋 전에 `schema.sql`이 76줄 바뀌었다는 것을 보고 멈췄다. 예상(약 10줄)과 다르면 커밋하지 않는다.
3. **같은 것을 두 가지 방법으로 확인한다.** 함수 개수(40개), 지워졌던 함수가 실제로 있는지, 마이그레이션 파일과 글자 하나까지 같은지.
4. **실패 원인을 로그로 찾는다.** GitHub Pages 실행 #4가 실패했을 때 실행 상세 페이지의 로그를 열어 원인(Jekyll이 node_modules 마크다운을 처리)을 찾았다. 추측하지 않았다.
5. **고치고 나서 실사이트에서 확인한다.** 배포 후 번들 이름과 기능 문자열이 실제 사이트에 있는지 확인했다(08fb77c5).
6. **민감한 값은 가린다.** 관리자 링크 전체 문자열을 문서에서 지우고, 검사 명령도 패턴(`b7sh[a-z0-9]{12}`)으로만 쓰도록 바꿨다.
7. **도구가 안 될 때는 우회하지 않는다.** 편집기 실행이 안 되면 멈추고, 원인과 대안을 보고서에 적어 회신을 받았다.
8. **테스트 데이터는 접두어로 구분하고 끝나면 지운다.** `TST`, `tst` 접두어만 지우고 실제 직원은 건드리지 않는다.
9. **보고는 근거와 함께 한다.** "됐다"가 아니라 확인한 값(예: 직원 2명, 세션 1개)을 적는다.

## 2. 하이쿠가 배워야 할 핵심 (지금부터 적용)

| 상황 | 오퍼스가 한 것 | 하이쿠가 할 것 |
|---|---|---|
| 파일을 기계적으로 바꿨을 때 | diff 크기를 보고 멈춤 | `git diff --stat`을 커밋 전에 항상 본다 |
| SQL 함수 블록을 자를 때 | 함수 개수와 파일 비교로 검증 | 함수 개수를 세고, 자른 블록이 마이그레이션과 같은지 확인한다 |
| DB에 손댈 때 | 읽기 전용 스냅샷 먼저 | L1 전에 L0 기준값이 있어야 한다 |
| 배포 후 | 실사이트 번들과 문자열 확인 | "배포됨"이라고 쓰기 전에 실사이트를 확인한다 |
| 도구가 막힐 때 | 멈추고 회신 요청 | 같은 방법을 3번 이상 반복하지 않는다 |
| 민감한 값 | 문서에서 가림 | 링크·키 전체 문자열을 어디에도 쓰지 않는다 |
